# WATA MCP — инструкция для AI-агента

Этот репозиторий даёт полный программный доступ к аккаунту платёжной системы
**wata.pro**: личный кабинет мерчанта, кошелёк, выплаты, терминалы, транзакции,
цифровые товары, а также публичный API эквайринга и цифровых товаров.

90 инструментов: авторизация (4), личный кабинет (61), публичный API эквайринга (10),
приём и проверка вебхуков (3), публичный API цифровых товаров (12).

## Быстрый старт

```bash
npm install && npm run build
node dist/cli.js install        # прописать MCP-сервер в конфиг твоего агента
node dist/cli.js login          # вход: почта, пароль, код из письма
node dist/cli.js doctor         # проверить, что доступ работает
```

Если ты запускаешься неинтерактивно, вход делается в два шага:

```bash
node dist/cli.js login --start              # спросит код у пользователя по почте
node dist/cli.js login --code 123456        # код, который сообщит пользователь
```

## Что нужно от пользователя

Только одно из двух:

1. **Почта и пароль** (`WATA_EMAIL`, `WATA_PASSWORD`) — плюс код из письма при входе.
2. **Готовая cookie-строка** из DevTools в `WATA_COOKIE` — если пользователь не
   хочет сообщать пароль.

Дополнительно, только для публичного API эквайринга и цифровых товаров: `WATA_ACQ_TOKEN`
(JWT-токен терминала).

**Никогда не записывай эти значения в файлы репозитория.** Репозиторий публичный.
Секреты живут в `~/.wata-mcp/` и в `.env`, который закрыт `.gitignore`.

## Два независимых способа авторизации

Это два разных мира API, и путать их нельзя.

1. **Сессия кабинета** (`WATA_EMAIL`/`WATA_PASSWORD` или `WATA_COOKIE`) — нужна
   всем инструментам без префикса `wata_acq_`, `wata_dg_`, `wata_webhook_`:
   терминалы, транзакции, кошелёк, выплаты, чарджбеки, тикеты и т.д. API-ключ
   WATA выпускается **на терминал** и НЕ даёт доступа к кабинету целиком —
   кошелёк, выплаты и настройки через него недоступны в принципе. Поэтому
   основной режим здесь — вход по почте и паролю, а не по API-ключу.
2. **JWT-токен эквайринга** (`WATA_ACQ_TOKEN`) — нужен только инструментам
   `wata_acq_*` и `wata_dg_*` (публичный API эквайринга и цифровых товаров).
   Сессия кабинета для них не требуется и не используется. Токен выпускается
   через `wata_terminal_api_token_create` (нужна сессия кабинета) или пользователь
   даёт готовый.

## Песочница

`WATA_ENV=sandbox` переключает публичный API (`wata_acq_*`, `wata_dg_*`,
`wata_webhook_*`) на `api-sandbox.wata.pro` вместо боевого `api.wata.pro`.
**У песочницы свой публичный ключ вебхуков**, отличный от боевого:
`wata_webhook_public_key` и `wata_webhook_verify` учитывают `WATA_ENV` сами,
кэшировать один ключ на оба окружения нельзя.

`WATA_ENV=sandbox` переключает и личный кабинет: адрес меняется с
`merchant.wata.pro` на `merchant-sandbox.wata.pro`. **У песочницы отдельные
учётные данные** — боевые логин и пароль там не подойдут, вход нужно
выполнять заново. Сессии хранятся раздельно (`~/.wata-mcp/session.json` для
боевого окружения и `~/.wata-mcp/session.sandbox.json` для песочницы), так
что переключение `WATA_ENV` не затирает сессию другого контура.
`node dist/cli.js doctor` первой строкой печатает, в каком окружении сейчас
работает клиент.

## Особенности, о которые легко споткнуться

- Кабинет требует заголовок `RequestVerificationToken` на **каждом** запросе,
  включая GET. Без него приходит `400` с пустым телом. Клиент чинит это сам.
- Перед сайтом стоит DDoS-Guard. Не устраивай шквал запросов: интервал
  настраивается через `WATA_MIN_REQUEST_INTERVAL_MS` (по умолчанию 350 мс).
- Пагинация двух видов: `{totalCount, items}` и курсорная
  `{hasNextPage, nextCursorId, nextCursorDate}`. У транзакций и чарджбеков — вторая.
- Вывод средств из кошелька — **трёхшаговый**: `calculate-commission` →
  `initiate` → `confirm`. Третий шаг необратим. **Не вызывай `confirm`
  без явного указания человека** — это необратимая операция с деньгами.
- Вывод на карту через API невозможен: реквизиты карты передаются только
  через виджет WATA, `initiate/card` принимает лишь `orderId` и `quoteId`.
- Лимиты вывода (`wata_wallet_withdrawal_limits`) требуют обязательных
  query-параметров — без них сервер отвечает «Ваш запрос недействителен».
- Подпись вебхука — **SHA512withRSA**, а не SHA-256, и проверяется по
  **сырому телу запроса** (raw body), а не по распарсенному JSON: любая
  пересериализация ломает проверку.
- Приём вебхуков включается через `wata_terminal_update` (`webhookUrl`,
  `sendPayWebhook`, `sendPayWebhookOnDecline`, `sendPrePayWebhook`,
  `sendRefundWebhook`). У предоплатного вебхука (`sendPrePayWebhook`) —
  **таймаут ответа 10 секунд**: не успел — транзакция отклоняется без
  обращения в банк, ретраев по нему нет. Постоплатный и возвратный вебхуки,
  наоборот, ретраятся с нарастающим интервалом до 32 часов — обработчик
  обязан быть идемпотентным и отвечать `HTTP 200`.

## Скиллы

В каталоге `skills/` лежат одиннадцать скиллов по доменам: `wata-setup`,
`wata-terminals`, `wata-transactions`, `wata-links`, `wata-wallet`,
`wata-payouts`, `wata-chargebacks`, `wata-digital-goods`, `wata-support`,
`wata-acquiring`, `wata-webhooks`. Начни с `wata-setup`.

## Если инструмента не хватает

Кабинет содержит больше эндпоинтов, чем покрыто типизированными инструментами.
Универсальный доступ даёт `wata_raw_request` — тот же путь, та же авторизация,
та же защита. Полный список известных эндпоинтов кабинета — в `docs/api-map.md`,
описание публичного API эквайринга и цифровых товаров — в `docs/public-api.md`.
